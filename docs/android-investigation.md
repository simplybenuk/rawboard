# Android API investigation

Checked 20 October 2026 against official Android documentation. These findings informed a native Kotlin implementation without Compose, a foreground service or an audio-upload pipeline.

## On-device speech

[`SpeechRecognizer`](https://developer.android.com/reference/android/speech/SpeechRecognizer) exposes `isOnDeviceRecognitionAvailable` and `createOnDeviceSpeechRecognizer` from API 31. This is the explicit local recognizer API. The generic `createSpeechRecognizer` can select a provider that uses remote servers; this app never calls it. Pixel hardware and Gboard's own dictation features do not prove that a third-party keyboard gets the same recognition behavior.

API 33 adds `checkRecognitionSupport` and `triggerModelDownload`. [`RecognitionSupport`](https://developer.android.com/reference/android/speech/RecognitionSupport) reports installed, pending and supported on-device languages separately. Setup checks en-GB and can request a download. A support-check error does not establish that dictation is unavailable. A download request is not proof that the model is ready.

[`RecognizerIntent`](https://developer.android.com/reference/android/speech/RecognizerIntent) documents segmented recognition and silence-duration hints. Their behavior depends on the provider. This prototype requests segmented sessions on API 33+, with eight seconds of complete silence and a 60-second minimum as hints. It imposes its own two-minute maximum and an eight-second finalization timeout. If an initial segmented request gets a client/support rejection, the next explicit microphone tap tries ordinary on-device recognition. There are no hidden automatic restarts. Long pauses and several minutes of natural dictation must be measured on the Pixel. The public API cautions against continuous recognition.

[`RecognitionListener`](https://developer.android.com/reference/android/speech/RecognitionListener) distinguishes changing partial hypotheses from final session results and finalized segments. The app replaces partial text, appends final segments, ignores a repeated whole-session result after segments, and asks the user to confirm unfinished hypotheses after interruption. Every callback belongs to a generation; cancellation invalidates that generation. A canceled recognizer cannot populate another editor's draft.

No API guarantees verbatim disfluencies or perfect transcription. The app requests free-form English and avoids an extra formatting pass that could hide fillers. Raw+ receives whatever words the recognizer actually returned, not an audio-derived verbatim record. No audio file is created, so lost speech cannot be retranscribed later.

## IME lifecycle and microphone

[`InputMethodService`](https://developer.android.com/reference/android/inputmethodservice/InputMethodService) supplies the keyboard view and current `InputConnection`. The app requests `RECORD_AUDIO` from its setup Activity, then starts recognition only after a microphone tap in a visible keyboard. It cancels capture and edits when the input view hides or editing ends. It does not add a foreground service to keep listening in the background.

The current IME has an exception to some [foreground-service background-start restrictions](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start), but that is not a general microphone permission bypass. [Audio input sharing](https://developer.android.com/media/platform/sharing-audio-input) can interrupt capture or deliver silence when another app takes priority. Calls, screen lock, microphone privacy toggle, revoked permission and keyboard changes remain device tests.

`commitText(selectedText, 1)` is the sole explicit host-write operation. The service never calls `performEditorAction`, sends Enter, or reads surrounding, selected or extracted host text. Because this IME never creates a composing region, it also omits the default finish-input implementations that would call `finishComposingText`. The host app controls whether and when its user submits content.

## Returning to Gboard

The supported API is `InputMethodService.switchInputMethod(id)`. The keyboard discovers an enabled Gboard entry through [`InputMethodManager.getEnabledInputMethodList`](https://developer.android.com/reference/android/view/inputmethod/InputMethodManager), then asks Android to select its returned ID. Gboard's package name identifies it; no component ID is hardcoded. Android still controls switching. If Gboard is missing or direct switching fails, the app opens `showInputMethodPicker()`. The cog menu offers both Return to Gboard and Choose keyboard, alongside Android's own navigation-area switch control.

## Panel size, navigation and long drafts

User feedback showed version 0.1.2's Insert overlapping Android's keyboard-switch globe. The panel forced an exact height without respecting its parent's measurement constraint. Version 0.1.3 clamps the requested size to the actual [`MeasureSpec`](https://developer.android.com/reference/android/view/View.MeasureSpec), and reserves residual navigation, caption-bar and display-cutout overlap inside the panel. Insets are returned unchanged. Calculations use panel and decor positions in the same window coordinates, so a framework ancestor's existing inset reservation is not added twice. The caption inset matters because [AOSP's IME navigation controller](https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/master/core/java/android/inputmethodservice/NavigationBarController.java) can report the larger keyboard navigation frame separately from the ordinary gesture bar. Android's own switch control is retained.

Expand changes the same panel's desired height and requests layout. It uses the available height with a small host-context gap, without starting an Activity, replacing the input view, requesting an editor restart or enabling extract/fullscreen mode. Expanded height never shrinks a short panel. The preview alone scrolls; controls stay outside it. Compact layouts move mode choices into the cog and reduce preview/status chrome. Unfinished-word confirmation replaces Insert rather than adding another row. Host apps can still restart their editor during resizing, so the existing restart-clearing policy remains a device acceptance check.

Live partial replacements and final words follow the bottom while following is enabled. Manual review pauses it; Latest resumes it. AI and original-preview selection starts review from the top. Deferred scrolling waits for text measurement and is invalidated by subsequent touch, text or scroll operations. These behaviors need touch, accessibility and expansion checks on the Pixel.

The visible panel's [`keepScreenOn`](https://developer.android.com/reference/android/view/View#attr_android:keepScreenOn) is true only while a usable editor is starting, listening or finalizing dictation. Idle, errors, Cancel, hiding, switching, field changes and destruction clear it. This uses the IME's visible window and adds no wake-lock permission or background microphone capture.

## Dictation cursor

Version 0.1.4 adds a custom insertion caret to a display-only TextView. It does not create an EditText, request focus, show another soft keyboard or provide an input connection. Tap positions use TextView's [`getOffsetForPosition`](https://developer.android.com/reference/android/widget/TextView#getOffsetForPosition(float,float)); drawing uses the text layout's line and primary-horizontal coordinates. The caret blinks only while attached, shown, enabled and displaying source text. It never depends on the IME window acquiring editor focus.

The draft owns a UTF-16 cursor clamped away from split surrogate pairs. Confirmed text inserts a paragraph at that offset and advances the cursor before the existing suffix separator. Partial and interrupted text project into the same position without mutating source. Cancel drops only provisional text; Keep confirms it there. Existing source slices stay intact, and boundary newline runs are topped up to two where needed. Insertions invalidate older AI results. Raw's displayed source is exact so caret offsets match; local terminal punctuation is applied only when inserting Raw.

AI text has no reliable character-for-character mapping back to the original. A tap on an AI preview first reveals its source, and the next tap chooses a source position. The following scroll view observes full child touch dispatch and can target the provisional cursor line rather than the end of the original suffix. Touch accuracy, blinking and accessibility behavior remain Pixel checks.

## Local test history

The user's later test-log request explicitly changes the original no-transcript-history scope. Logging defaults on in version 0.1.4 and is explained in setup. Confirmed source snapshots, accepted AI source/result pairs and successful inserted text are retained locally. Unconfirmed partials, audio, surrounding host text, host identifiers and credentials are excluded. An inserted event is not evidence of later publication or sending.

The journal uses a separate Android Keystore AES/GCM key and AtomicFile in noBackupFilesDir. It is bounded to 100 entries, 30 days and 4 MiB, with retention applied on the next read/write. A single keyboard worker writes immutable snapshots off the UI thread. A persisted generation is captured before enqueue and checked under a shared lock, so Clear or logging changes invalidate old queued events. Clear deletes only history and its separate key. The API credential store is unchanged.

The internal HistoryActivity is not exported. It offers a logging toggle, comparisons, Clear all and explicit JSON export through Android's document picker. Exported JSON is plaintext at the chosen destination. No upload or sharing occurs automatically. Export reads after destination selection, and failures preserve local history while explaining possible partial output. Android Keystore round trips, delete/queue races and document providers still need physical-device validation.

## Sensitive input

[`InputType`](https://developer.android.com/reference/android/text/InputType) identifies text password, visible-password, web-password and numeric-password variations. [`EditorInfo.IME_FLAG_NO_PERSONALIZED_LEARNING`](https://developer.android.com/reference/android/view/inputmethod/EditorInfo) signals private/no-learning fields. This prototype conservatively blocks all private and non-text fields as well as passwords. It has no conventional typing keys; Gboard remains available for these fields. Apps can mislabel fields, so the policy cannot identify every sensitive value.

## System theme and feedback screenshots

Version 0.1.2 uses Android's day/night resource qualifiers for colors and native widget themes. There is no app-wide night-mode override or added dependency. All custom colors resolve from the current context. The Activity uses platform light/dark Material parents, while the IME has a separate `Theme.DeviceDefault.InputMethod` parent and transparent window background to retain keyboard window behavior. System navigation appearance is reapplied when the input view attaches. Android's documented `InputMethodService.onConfigurationChanged` behavior regenerates the input UI when system configuration changes.

The user requested screenshots for feedback. The keyboard no longer sets `FLAG_SECURE`. Setup applies it only while an API-key/backend-token field has focus or unsaved contents, then removes it after credentials are cleared and focus leaves. This permits layout feedback while protecting credential entry. Saved credentials are never rendered in those fields. External host apps and device policies can still restrict screenshots. See [Android dark theme guidance](https://developer.android.com/develop/ui/views/theming/darktheme) and [`FLAG_SECURE`](https://developer.android.com/reference/android/view/WindowManager.LayoutParams#FLAG_SECURE).

## Editing boundary

Speech recognition has no dependency on AI editing. Raw works without a server or key. Following the user's explicit approval for a phone-only personal test, version 0.1.1 supports a user-entered OpenAI API key encrypted on the device with Android Keystore. This is a per-device user credential, never a shared service key or bundled APK secret. Direct requests use the fixed OpenAI HTTPS endpoint, original transcript, full Raw+ rules, mode, model and `store:false`. Redirects are disabled. The app never sends the API key to a user-configured backend.

Following the user's cost preference, version 0.1.3 starts and clears drafts in Raw, and selects Raw before every recording, including Dictate more. Recognition callbacks and unfinished-word confirmation never request editing. An AI mode tap or Retry is the only trigger. Every request still uses the original transcript. The vendored skill's default editing mode applies to AI prompt behavior; it does not override the user's local-first app setting.

The optional backend remains a separate provider with its own access token. A blank credential can be reused only for the same provider and endpoint. Provider/address changes require a new credential. Remote backend endpoints require HTTPS; loopback HTTP supports USB `adb reverse`. The user can forget the saved credential and encryption key. Existing encrypted 0.1.0 backend configuration is preserved during upgrade.

The app and server vendor the exact user's Raw+ skill. Its Git blob SHA was `28e610ec9b5e0d6dd85ba5283da21406cd5ec6ab`. Version 0.1.4 appends mirrored editing notes, prompt version raw-plus-2026-10-20.2, without changing the original skill. The notes narrow Raw+ to minimal cleanup and include preservation examples. The user's Unslop concepts restrict new AI phrasing rather than deleting the speaker's meaningful words or uncertainty. Precise instructions and examples follow the [official GPT-4.1 prompting guidance](https://developers.openai.com/cookbook/examples/gpt4-1_prompting_guide); tests establish prompt wiring, not output quality. Direct history records the app prompt version; a separately configured backend is marked backend-unverified because the app cannot establish its deployed prompt.

Both providers use the [OpenAI Responses API](https://developers.openai.com/api/docs/guides/text) with `store:false`, a small model and no automatic retry. API state storage and abuse-monitoring retention are distinct under [OpenAI data controls](https://developers.openai.com/api/docs/guides/your-data). The direct model is `gpt-4.1-mini`, available now but [scheduled for removal on 14 January 2027](https://developers.openai.com/api/docs/deprecations). [ChatGPT plan sign-in](https://developers.openai.com/siwc/quickstart) is not implemented in this version.

## Retired Gemini Nano experiment, version 0.1.5

The requested 0.1.5 prototype uses Google's [ML Kit Prompt API](https://developers.google.com/ml-kit/genai/prompt/android), rather than preset rewriting styles, so the same full Raw+ instructions and original transcript can be sent locally. The [device list](https://developers.google.com/ml-kit/genai) includes Pixel 10 with nano-v3; [system instructions](https://developers.google.com/ml-kit/genai/prompt/android/system-instructions) require v3 or later. Capability is checked at runtime and no API key enters this path.

The decisive restriction is Google's top-foreground-app requirement. Foreground services are explicitly excluded, and Android documents IMEs as visible processes. No public IME exception was found. Actual inference while LinkedIn is focused must therefore be treated as unsupported/unproven until tested, even if settings readiness and a foreground sample succeed. BACKGROUND_USE_BLOCKED has a fixed explanatory error, Raw stays available and no cloud fallback runs. See [Google's background rule](https://developers.google.com/ml-kit/genai#background-usage) and [Android process classification](https://developer.android.com/guide/components/activities/process-lifecycle).

The user subsequently reported setup success and keyboard failure on their Pixel test. This fails the keyboard compatibility acceptance check. The exact error was not supplied, so attributing this failure to BACKGROUND_USE_BLOCKED is an inference consistent with the restriction, not a captured diagnosis. Nano should not be relied on for the requested keyboard workflow. An app-owned inference runtime would be a separate candidate requiring integration and device validation.

The Java Futures adapter runs in an owned worker with per-operation model lifecycle, cancellation, timeout and stale-callback guards. It counts the exact instructions and JSON source, enforces the input/context limits, caps output and requires a single nonempty STOP response. It does not truncate or silently split the original. Model download and a synthetic foreground sample require separate explicit button taps. Speech recognition is unchanged.

[ML Kit privacy terms](https://developers.google.com/ml-kit/terms) document local input/output processing alongside Google performance/utilization metrics and update-related network contact. The packaged startup provider can initialize regardless of selected editing provider. This changes the original no-telemetry scope; the user explicitly accepted it and the experimental keyboard limitations for the 0.1.5 Pixel test. Providers and setup disclose the difference. A local-ready indicator is never labelled proof of host-app keyboard operation.

SDK metadata requires the updated Kotlin toolchain. The prepared build pins Kotlin 2.3.21, AGP 8.13.2 and Gradle 8.13 with verified checksum, retaining JDK 17 and API 31 minimum/API 35 target. Coroutines Android 1.11.0 addresses Google's beta3/beta4 download issue. See [AGP compatibility](https://developer.android.com/build/releases/agp-8-13-0-release-notes), [Kotlin compatibility](https://kotlinlang.org/docs/gradle-configure-project.html) and [ML Kit known issues](https://developers.google.com/ml-kit/known-issues).

## App-owned llama.cpp, version 0.1.6

The user requested removing Nano after its keyboard test failed, then trying llama.cpp. This version removes the ML Kit dependency, coroutines transitives, Nano code, AICore binding and SDK startup/diagnostics components. Existing stored NANO selections map to LLAMA, not to a cloud provider. The saved cloud credential and consent remain separate.

The [official Android integration](https://github.com/ggml-org/llama.cpp/blob/master/docs/android.md) supports app-owned native inference. A minimal unmodified source subset is vendored at revision `39da130fcd1b6ca47d3c0522a40eccff41ea3dfb`; its source archive checksum and retained licenses are in `third_party/llama.cpp/RAWPLUS_UPSTREAM.txt`. An app JNI bridge uses only the CPU backend, no server, HTTP client, GPU dependency or AICore request. Kotlin owns cancellation/stale-result guards and off-main execution; native sessions own a deadline, cancellation checks and temporary model/context allocations.

For the first test, accept only the official [Qwen2.5-1.5B-Instruct GGUF](https://huggingface.co/Qwen/Qwen2.5-1.5B-Instruct-GGUF), Q4_K_M, model revision `91cad51170dc346986eccefdc2dd33a9da36ead9`. It has 1.54B parameters and an Apache 2.0 license. The pinned file is 1,117,320,736 bytes, SHA-256 `6a1a2eb6d15622bf3c96857206351ba97e1af16c30d7a74ee38970e434e9407e`. This is a bounded baseline, not a claim that it is the best available model. Exact size/hash/header checks apply equally to explicit downloads and file-picker imports. Model files are excluded from backups. Replacements are staged and verified before rename; interrupted operations retain an installed model.

The native engine applies the model's chat template to the same full Raw+ system instructions and JSON original source used by OpenAI. It counts the formatted tokens, refuses an overlong input without truncation, uses up to an 8,192-token context and 2,048 generated tokens with greedy sampling, and accepts only a completed end-of-generation result. Literal Qwen chat-boundary markers in source are rejected with Raw retained. The deadline includes load, waiting for another local inference, prefill and output generation. UTF-16/UTF-8 conversion preserves supplementary characters. Native log callbacks discard text, and user-facing errors use fixed messages.

Own-process inference avoids AICore's specific foreground service restriction. Android can still reclaim memory or restart an IME; only actual keyboard testing can establish responsiveness, speed, power use and survival under pressure. The app loads/releases the model for each request rather than retaining a gigabyte of weights between drafts. Raw defaults and explicit mode taps remain unchanged. A cancel control returns to Raw, and local inference never chooses a cloud provider.

The real host smoke revealed a Raw+ result that deleted a meaningful clause. The local adapter now rejects nontrivial word changes in Raw+ before accepting a preview. It compares bounded Unicode word/contraction/symbol sequences after case/apostrophe normalization, allowing only known hesitation tokens and adjacent exact repetitions up to eight tokens to disappear. It preserves order and catches that concrete regression, added words, missing uncertainty/negation and changed numbers or symbols. This deliberately rejects some otherwise valid transcription repairs. Punctuation and emphatic repetitions can still change meaning, so it is not a semantic guarantee. Polished remains outside this word filter, and the base skill and shared cloud prompt are unchanged.
